# 注释与说明文字：只写当下成立的事实

源码注释、测试夹具注释、`nix/` 脚本注释、`docs/` 主题页都按这一条口径：
**读者只应看到「这段代码今天做什么、为什么这样做、碰坏会怎样」，看不到它是第几阶段
做出来的、之前长什么样、以后打算做什么。**

过时的信息比没有信息更糟：它让读者按错误的印象改代码，而纠正成本要等到下一次踩坑。

## 该写什么

- **当下的行为与职责**：这段代码做什么、边界在哪（`-- |` 是 docstring，进 `vuna doc`）。
- **为什么这样做**：约束来源（类型系统、QTT、效应行、ABI、平台）、必须保持的不变量。
- **陷阱与破例后果**：不做某件事会怎样；某个参数为什么必须是这个值。
- **性能口径**：可复现的复杂度/实测来源（写成「O(n²) 因为每次 X 都扫全表」这类**因果**，
  而不是「比上一版快」）。
- **仍开放的限制**：只有指向 `docs/reference/debt.md` 里**当前仍存在**条目的编号才允许出现，
  且必须与「当下的限制」写在同一句；债务关闭时同步删掉编号。

## 不该写什么（写进注释就是债）

| 类别 | 例子 | 换成 |
| --- | --- | --- |
| 阶段 / 里程碑 / 任务编号 | `-- M38：...`、`（M34.5 收尾）`、`（A14）`、`（S3 新增导出）`、`（N1 提交 4b）` | 直接写这件事本身：`-- 线性捕获标记（binder 名编码）` |
| 实现史 | `旧实现把整项按深度 0 quote，产生错位索引` | `cutoff 必须是 0：shift 下钻 binder 时会自动抬高 cutoff`（写**现在必须怎样**） |
| 迁移/替换记录 | `从原 1227 行 Core.vuna 拆出`、`合并后只有一棵树`、`已删除 X`、`曾用 Y` | 删掉；结构调整的原因若仍成立就写成一句职责/不变量 |
| 未来计划 / 排期 | `后续会`、`下一步`、`待 M3b 落地`、`暂时` | 删掉；确有未关闭缺口就登记 `debt.md` |
| 版本号 / 提交号 / 日期 | `2026-11 起`、`在 239f525 被取代`、`cache v2 与旧 v1` | 只留**与行为有关**的 schema 号，并且只写当前值 |
| 会漂移的定位 | 行号、`原 XXX.vuna` 这种已不存在的路径 | 用符号名或 `vuna map find` 可查的模块名 |

判断标准：这句话**换个实现方式就会变假**吗？会，就不写；只有「换成另一种实现仍然必须
成立」的约束（类型面、ABI、编码格式、不变量、平台限制）才值得留在注释里。

回归保护交给测试，不交给注释：怕后人改回去，就加/留一条 steps 或夹剧来锁行为，
而不是在注释里叙述「旧实现如何如何错」。

## 分类细则

- **源代码（`packages/compiler/`、`packages/base/`、`packages/cli/`）**：上面的表全部适用。删行是安全的。
- **测试夹具（`test/corpus/**/*.vuna`）**：注释只写「这条用例锁什么行为」。
  **行数不可变**——`.diag.json` 里存了 `(line, col)`，改写必须就地替换，不能增删行
  （需要增删时同步重新 `--bless-diag`）。
- **`test/suite/steps/*.steps`**：头注释只写章节主题与断言面。
- **用户可见字符串**（诊断模板 `tcTemplate`/`cgTemplate`、CLI `help`/`--help`、
  `errors.md` 文案）：不得出现编号；诊断消息描述的是**规则本身**
  （「case on Bool accepts only True, False, or variable patterns」），不是「哪个里程碑还没做完」。
- **`docs/reference/*.md` 主题页**：描述现状与不变量；**不写里程碑编号、不写「后续路线」**。
  终态方向集中在 [`docs/architecture-target.md`](../../docs/architecture-target.md)，
  未关闭缺口集中在 [`docs/reference/debt.md`](../../docs/reference/debt.md)。
- **`.agents/`、`nix/`**：规则/脚本注释同样只写当下口径；门槛脚本的「标定历史」只保留
  方法与当前值，逐轮记录留在 git 历史。
- **`nix/checks/data/context.budget` 这类阈值文件**：写清指标定义与当前值即可，不要累积每轮改动的说明。

## 自检（改完扫一眼）

```console
# 1) 注释里的阶段 / 里程碑编号（应为空）
grep -rnE --include='*.vuna' '^\s*--.*\b(M|W|A|B|C|S|N|P)[0-9]+(\.[0-9]+)?' compiler base lib app test

# 2) 实现史与变更叙述（应为空）
grep -rnE --include='*.vuna' '^\s*--.*(旧实现|旧版|旧路径|历史上|曾经|原本|后来|过渡|spike|已删除|已废弃|不再使用)' \
  compiler base lib app test

# 3) 用户可见字符串里漏编号
grep -rnE '"[^"]*\bM[0-9]' compiler base lib app

# 4) 文档侧：主题页不应有里程碑编号或「后续路线」
grep -rnE '\bM[0-9]+(\.[0-9]+)?|后续路线|下一步|待实现' docs/*.md docs/reference/*.md README.md
```

**允许保留的编号**：`docs/reference/debt.md` 里**仍开放**的条目编号（如 `D33`），以及
[`docs/architecture-target.md`](../../docs/architecture-target.md) 的终态决策 `D1`–`D16`
（它们描述长期成立的设计，不是阶段）。其余编号（已关闭的债务、里程碑、里程碑内的子任务）
一律清掉。

一次 grep 有命中不代表一定违规（比如 `-- 旧的 `Base.IORef` 保留给…` 这类**当下仍然成立**的
并存关系），但要能说清「为什么这句今天仍然为真」。说不清就改写成当下的事实。

## 与「完成」的关系

清理注释不是一次性任务：**每次改动顺手守住**。改一段代码时，顺手把它头顶那句已不成立的
注释改对或删掉，比事后专门做一轮清理便宜得多。新增注释按本页口径从第一句就写对。
